# 真實之眼掃描、批次收納與契約驗證經驗

這是一份可匯入 GPT 檔案庫的實作經驗候選，不是已核准的 GEN2 Skill，也不代表已發布正式網站或 APK。本次以合成卡片測試，未讀寫 OWNER 手機存檔。使用者選擇先取得可匯入文件，沒有宣稱已上傳私人 GPT 檔案庫。

## 任務與順序

1. 先讓書櫃上的書進入原有漂浮軌道，驗證掃描器。
2. 全選掃描範圍內書本，長按三秒，確認後收進同一張既有空白卡。
3. 重整，驗證原 ID、收納成員及卡片數量不變。
4. 長按原收納卡，實體化還原；再長按同卡，重新卡片化。
5. 用既有「解除契約」法術卡解除，確認原物件恢復、原收納卡保留、施法卡按原規則被吸收。
6. 相同步驟擴展至整個已登記圖書館場景與書本，最後交由 OWNER 手機驗收。

## 原始缺陷與判斷方式

- 原掃描器只查 `bookEntities`。場景中有模型卻未被查詢，不等於模型壞掉；先分辨「未登記候選」「距離／扇形排除」「模型命中失敗」。
- 原選取標記不參與 raycast。即使標記顯示掃到物件，長按仍要求命中原模型，薄小或難觸控的模型仍難操作。
- 原 books 長按完成後只播放六芒星預覽，沒有正式批次契約。修正手勢不能代替補完資料與還原閉環。
- 原扇形顯示起點與實際方位判斷不一致；改成同一個置中扇形定義。
- 原長按 `pointerup` 一律取消。裝置忙碌時，滿三秒的計時回呼可能尚未處理；補上鬆手時再核對經過時間，取消事件仍取消。
- 初次整館動畫直接移動人物控制根節點，會讓系統判斷人物在儀式期間移動而拒絕交易；改為移動人物外觀子模型，保留控制錨點。

## 實作契約

- `scan-bundle.js` 與既有 ObjectCraft 共用 `living-library-player-objects-v1`，不建第二份正式卡片資料庫。
- 原空白卡 ID 保留，`scanContract.members` 僅保存允許的 `{kind,id}`；不複製私人 MD、Mesh、程式或 Token。
- `runeBinding` 使用同一收納卡的契約 ID，沿用既有解除契約規則。卡片化與實體化只切換 `form=card/world`；解除契約則移除對應契約 metadata。
- 卡片 revision、空白卡資格、成員身分、重複所有權與可用性均檢查。初次媒介必須是人物三單位內最近唯一的未使用空白卡；近距離並列候選拒絕。
- 動畫結束才作單次 localStorage 寫入；存檔失敗或資料衝突不憑動畫宣告成功，不新增卡 ID。
- 持續繪製、圖鑑及書本自己的更新器之後套用收納可見性，避免下一幀重新顯示已收納模型。
- 新增於現有掃描器：離架召喚、範圍全選、三秒收納入口，以及書本／場景／兩者的選擇。半徑、角度、方位仍可調，儀式期間拒絕改動。

## 掃描範圍與實際涵蓋

半徑 2–20 是場景單位（介面標 m）；角度 15–360 度；方位以世界 -Z 為零度、+X 為 90 度。採水平範圍，沒有宣稱三維遮蔽或高度掃描。分組場景用登記時的幾何中心，書本使用當前模型位置。

合成測試基線為 15 本公開書，加上 28 組場景物件，共 43 個掃描單位。場景包括地台、同心環、格線、7 座書櫃、7 組石柱、5 盞燈、天穹環飾與放射飾條、人物外觀、光源與粒子；每組可包含多個原模型，43 並非 Mesh 總數。

掃描器自身、散落的玩家卡、私有 GEN2 投影不納入此次批次集合；已有獨立契約的初始法陣保留原契約，避免雙重綁定。新增場景需明確登記穩定 ID，不能把本次登記清單誤認為任意未來模型都能自動收納。公開功能與書內閱讀入口保持可用，收納不刪除目錄定義。

## 可重用驗收清單

每個物件型別都應沿「候選登記 → 範圍判斷 → 可點選 → 三秒長按 → 明確確認 → 動畫 → 原子保存 → 原 ID 重讀 → 實體化 → 再卡片化 → 解除契約 → 原物件恢復」驗證；每一步分別保存證據，失敗時定位哪個層次，不能用一個動畫或單元測試 PASS 代替整條閉環。

OWNER 驗收時先用候選環境的新空白卡；範圍設 20、角度 360、書本模式按 ⇧ 離架，再按 ⊙ 全選與長按 🔯；確認後檢查原卡與數量，長按原卡還原／再收納，最後使用解除契約卡。書本通過後，改選「書本與場景」重做同一套流程。保留所有原存檔，不把合成測試資料匯入手機。
