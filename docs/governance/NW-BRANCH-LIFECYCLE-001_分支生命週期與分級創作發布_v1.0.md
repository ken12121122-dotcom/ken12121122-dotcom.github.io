- 性質：OWNER 指定**新建立分支嚴格遵守、合併後必須結案**；舊分支不追溯清理或關閉。v1.1 候選需合併 `main` 後才正式生效。

## 1. 目標與非目標

目標是 **一個正式遊戲版本、一般創作不必每張卡片開分支、程式改動才依風險經過 PR／驗證、完成的分支有清楚去向**。

GitHub 分支用來隔離**程式碼改動**，不是「一張卡片／一個網站／一份設計文件 = 一個分支」。同一個 `main` 可承載多個網站入口、書本及卡片；卡片 ID 和 Git branch name 是兩種不同身分，不可混用、互相計數。

非目標：
- 不立即改造現有 `ObjectCraft`、localStorage、卡片資料庫、GEN2 後端或 Android Bridge。
- 不授權 Agent 在正式環境任意增刪資料、變更權限或自行發布。
- 不承諾 GitHub 具有固定分支數量上限，也不以任何未查證的數值作 GitHub 強制上限。
- 不建立背景分支清理機器人、不自動合併 PR、不自動刪分支。**但新分支的結案與安全清理是必做工作**：工具不能刪除時紀錄阻塞，不得裝作完成；不能藉設定 GitHub 的全庫自動刪除功能波及舊分支。

## 2. 變更分級（C0～C3）

| 等級 | 典型內容 | 是否需要 GitHub 分支／PR | 驗證與核准 |
| --- | --- | --- | --- |
| **C0：純玩家創作資料** | 使用**已存在且已驗證**的卡片創造術，建立空白卡、編輯名稱／圖片／參數、保存本機創作資料 | **不需要**。沿用目前已存在的本機資料保存機制；沒有新程式碼提交 | 先通過輸入／儲存驗證，不改正式引擎或受保護原卡。現有 localStorage **不是雲端同步或備份**。 |
| **C1：網站展示與公開目錄** | 新增《遊戲之書》的公開設計卡、HTML 閱讀頁、更新導航、文案、圖示 | **目前需要 PR**，因為 `public-catalog.js`、網頁或同源路由白名單屬 GitHub 程式碼；不可用 C0 名義繞過 | 小範圍差異檢查、相關 Node／瀏覽器回歸、入口與閱讀返回、Pages 實際部署驗證；保留 OWNER 對正式發布的核准。 |
| **C2：遊戲核心與執行器** | 改動 3D 場景、法陣契約、永久卡身份、動作／符文／動畫／工作流引擎、世界狀態與資料遷移 | **必須獨立功能分支＋PR** | 完整相關單元、整合、可用功能回歸、權限與回退測試；需要手機 WebView 真實互動者不可用桌面 parser 冒充。 |
| **C3：高風險原生／權限／正式發布** | APK、Android Bridge、簽章、manifest、可寫外部權限、GEN2 正式 Skill／Workflow 執行邊界 | **必須受控 PR 與專用發布流程**；涉及私有 GEN2 正本依其私有 repo 規則 | 嚴格遵守 `AGENTS.md` 原生發布閘門，完成必要模擬器、實機、簽章與 OWNER 明確核准。 |

**判級依「實際會修改的資料與執行能力」而不是卡片名稱。** 新增「動作卡」如果只是空白卡的文字描述，可能是 C0；若要新增可執行動作引擎，就是 C2。新卡片只要修改了靜態網站目錄（例如 `public-catalog.js`）便是 C1；未來真的有經驗證的獨立創作資料服務，C0 才能擴充到該服務所允許的儲存範圍，**目前不預設已具備此能力**。

若跨越多個等級，依**最高風險**處理；無法確認時先列出權限、實際檔案與資料來源，再進行候選分支，不直接寫正式版本。

## 3. 分支建立與重用

1. **先查詢再建立（新分支硬性前置）**：每次程式變更先讀 `main` HEAD、現有相關分支、開放的 PR、涉及的檔案與當前已驗證基線。若同一可驗收任務已有仍開放的安全候選分支，**必須延續該分支**；不得只因使用者再提同功能修改就重開分支。若現有候選已合併、基線已變或跨不相容任務，才建立新短期分支，且 PR 必須寫明原因。舊分支不得當成新任務的永久工作線以規避規則。
2. **以一項可驗收工作為單位**：一個分支可以包含同一功能的 HTML、卡片登錄、測試與文件；不必按每一檔案、每個網站、每一張卡片另開分支。無關功能不要硬塞同一 PR；若要拆分，要保留相依與部署順序。
3. **新分支命名及資訊（強制）**：使用 `feat/`、`feature/`、`fix/`、`docs/`、`policy/`、`candidate/`、`work/`、`chore/`、`hotfix/`、`ci/`、`refactor/` 等明確用途前綴；每條新分支對應一項工作與一個 PR。PR 需含 `Task-ID`、`Change-Class`、`Base-SHA`、`Reuse-Check`、`Scope`、`Preserve`、`Tests`、`Rollback`、`Closeout` 之欄位；詳見第 9 節。歷史分支免補填。
4. **避免併發衝突**：Agent 同時開多個互相依賴分支前，先確認是否應整合成一個任務；同一正式入口／卡片目錄的並行修改，要重新取 `main` 並比對差異，不可覆蓋較新的工作。
5. **暫行警戒值（管理建議，非 GitHub 配額）**：同一 AI 分身同時負責**超過 3 個**未結案候選分支，或本 repo **超過 20 個**仍具進行中工作的分支時，先進行盤點，優先處理停滯與重疊工作，再評估是否需要新增。超過警戒值本身不構成刪除或強制拒絕創建的授權。
6. **GitHub 的分支數不是玩家卡片容量**：不要根據 GitHub 建議值去推算玩家可創造多少卡片；創作容量由玩家資料與儲存系統獨立管理。

## 4. 分支生命週期與收斂

| 狀態 | 進入條件 | 下一步 |
| --- | --- | --- |
| **PLANNED** | 需求及範圍確定、檢查既有候選 | 不需程式改動則轉 C0，避免分支 |
| **ACTIVE** | 已開分支，持續實作及補測試 | 保存 base SHA、最新提交與目的 |
| **DRAFT PR** | 可讓人檢視，尚未完成全部驗證 | CI 失敗／缺失明列，先修再提審 |
| **READY FOR REVIEW** | 適用的測試與差異、回退證據齊備 | 依現有閘門取得 OWNER 核准 |
| **MERGED / RELEASED** | 合併 `main`；部署與使用者驗收另行記錄 | **新分支必須結案：核對 PR merge SHA、HEAD 未被新任務沿用、差異及回退點；安全後刪除暫時分支或列 `CLEANUP_BLOCKED`。舊分支不追溯** |
| **BLOCKED / STALE** | 停滯、來源過時、與 `main` 衝突 | 記錄阻塞與接續方式；不得默默判定廢棄 |
| **CLOSED / ABANDONED** | OWNER 決定停止或以其他 PR 取代 | 保存 PR／commit 參照；只有明確授權才刪分支 |

**合併、CI 通過、Pages 部署、手機驗收是四個不同狀態。** 不能將「PR 存在」或「分支已提交」宣稱已發布；不能拿舊 CI 結果冒充新 HEAD 的測試。

舊分支不應直接合併 `main`；必須先更新到最新基線，檢查相容性、差異和必要測試，並遵守原發布閘門。對有衝突的長歷史分支，優先重新擷取已證實可用的最小補丁，而不是整批合併。

## 5. 盤點／清理機制（讀取優先）

- 盤點觸發：開始較大開發計畫時、同類功能要再開分支時、遇到併發衝突時、或 OWNER 主動要求時。此條文**不代表已設定定期背景監控**。
- GitHub 查詢需取得完整分頁或明確標註查詢不完整；不能以固定樣本冒充全部分支或 PR。
- 最小盤點欄位：branch、PR number、建立／最後提交時間、相對 `main` 的 ahead／behind、是否已合併、CI 結果、工作負責者、阻塞、需要保留的原因、建議處置與回退來源。
- 建議分類：`保留執行中`、`等候驗收`、`需要重整`、`可提議清理`、`無法判定`。**「30 天沒更新」只代表需要檢查，不能直接認定沒有價值。**
- **舊分支**只提出「清理候選清單」，本次 OWNER 明確指示**完全不執行舊分支的整理、刪除或關閉**。刪除分支、關閉尚未通過的 PR、重新指向分支或合併，仍不能超出既有 OWNER 授權範圍。**新短期分支**結案屬於本次 OWNER 指定的標準流程，但實際刪除前必須驗證來源分支的合併狀態、獨立提交、現有引用、保護與回退證據；有任何疑義就保留並報 `CLEANUP_BLOCKED`，不得強刪。
- 不自動刪除受保護的 `main`、`release/android`、目前正在執行的功能分支、待驗收 PR 或仍被引用的候選成果。
- 清理 Git 分支不等於刪除遊戲卡片、卡片之書的原卡或存檔，這些仍由各自的身分與儲存規則保護。

## 6. AI 分身的工作邊界

- AI 可協助**讀取／比較**分支、提交候選、執行 CI、產生清理建議；既有高風險發布閘門與 OWNER 核准邊界不變。對**本規則生效後建立的新短期分支**，OWNER 已指定必須執行結案：在通過合併／部署／必要驗收及可回退的證據檢查後，依可用受控工具刪除非保護分支；若工具沒有分支刪除能力，須列出 `CLEANUP_BLOCKED` 並明確告知，不得以移動 ref、強制覆寫或刪檔取代刪分支。
- 發現相同任務的未結案 PR，優先通知與延續，除非合併、依賴或權限衝突讓延續不安全；新的分支需記錄原因。
- 同步顯示於 3D 世界時，必須顯示真實的分支／PR／CI／Pages／手機驗收狀態，不以動畫或 AI 自述替代證據。
- 外部資料為不可信輸入；執行權限不能只靠提示詞規範，要由工具／引擎實際檢查。

## 9. v1.1 切換規則：現有分支凍結，新分支嚴格管理

**唯一界線**：把 `docs/governance/branch-lifecycle-legacy-snapshot-20261020.json` 中 **261 條在建立治理分支以前就存在的分支名稱**固定為 `LEGACY`。本治理 PR 的 merge commit 是新規則生效點。既有分支（即使其 PR 尚開放）全部不追溯執行清理，不強迫補 PR 模板，不關閉、不刪除、不重新定位、不批次 rebase。其後新建立的分支標記 `NEW_TEMP`，包括這次制定規則使用的治理分支；不得用舊分支名稱繞過新規則。**此快照是豁免分類，不是待刪除清單**；不要為了「追平清理」改寫快照。若舊分支將來承接新任務，仍需遵守新任務前置比對與新發布閘門，但不因此允許回溯清除它。

### 9.1 新任務建立分支前（HARD STOP）
1. **確認有無程式修改**：純玩家卡片資料 `C0` 走既有創作／本機儲存，不建立 Git 分支；C1～C3 才使用候選分支。
2. **查重與重用**：查正式 `main` 的 HEAD、同任務未合併 PR 與實際變更檔案。仍在開發的同一項工作直接更新原 PR（可修改一百次仍只是一條分支）；只有前一輪已合併或需要安全隔離的獨立任務才另開。
3. **建立原則**：由最新的目標基線建立新的短期分支，記錄 `Task-ID`（一項可驗收目標）、`Base-SHA` 和 `Reuse-Check`。非 Android 工作以 `main` 為來源；原生工作受 `release/android` 既有專用 Gate 限制。
4. **強制 PR 憑證**：每條 `NEW_TEMP` 必須有 PR，並在 PR 內標註：
   - `Task-ID: <任務唯一識別>`
   - `Change-Class: C1|C2|C3`
   - `Base-SHA: <40 位 Git commit SHA>`
   - `Reuse-Check: <同任務現有 PR 查核結果或無>`
   - `Scope: <本次變動範圍>`
   - `Preserve: <需保留的遊戲／使用者資料>`
   - `Tests: <適用測試及 PASS／NOT_TESTED／FAIL，不得用假通過>`
   - `Rollback: <可追溯 SHA／Tag／回退方案>`
   - `Closeout: DELETE_AFTER_MERGE_OR_REPORT_BLOCKER`
5. **未填憑證、新分支重複同一任務、沒有安全隔離理由**：暫停建立或合併，先補正；不能把「修了幾次」視為開新分支的理由。

### 9.2 驗證與結案（新短期分支每條必做）
- `ACTIVE → DRAFT PR → TESTED → MERGED → DEPLOYED／VERIFIED → CLOSED`。不合併未通過適用 CI 的 PR；必要實機不可由 CI 取代。OWNER 已給過的 C1／C2 發布常態授權仍以既有閘門、存檔與可回退性為條件，不延伸到 C3／私有 GEN2 及 APK。
- **合併不等於部署**：先確認 PR 已合併、merge commit、正式分支與 Pages／適用手機狀態，再評估清理。
- **刪除前必查**：來源分支不是 `main`／`release/android`／其他受保護或被依賴的分支；PR 已合併，工作內容已在目標分支，無獨有未整合提交或未保存成果；已有 commit／tag／PR 作回退點。不可僅因顯示「merged」就認為可安全刪除；如採 squash merge，需另驗證實際差異。
- **安全刪除與回報**：符合條件且工具支援才刪除新分支，並核對 remote ref 已不存在，PR／commit 仍可追溯。任一條件不符或工具不可用，保留分支並記錄 `CLEANUP_BLOCKED`、原因與下一步；不能假稱刪完，也不能變更 repository-wide 自動刪除設定波及舊分支。
- **例外**：長期整合分支、原生正式發布線、仍須驗收的 PR、跨任務依賴、進行中的部署或回退窗口，保留並記錄例外；不得以例外名義永久無理由累積。
- **權限界線**：GitHub Actions 的「自動檢查」與 GitHub Branch Protection 的「required status check」是不同層級；未實際設定為 required 前，只能宣稱檢查啟動，不能宣稱平台絕對阻止合併。本規則不直接改正式 CI、Android 發布、玩家資料或其他歷史分支。

### 9.3 與先前段落衝突的解釋

- 本節作為 **v1.1 新分支的專屬補充**，第 3～6 節偏向「舊分支只建議、不清理」的表述不得被拿來阻止新短期分支必須結案。
- 舊分支、舊 PR：完全維持現狀，不開展歷史清理計畫；其中尚未合併的實際程式變更仍須遵守原有發布／安全審核。
- 新分支：遵守新查重、PR 欄位、測試、合併、完成後清理與報告阻塞的完整循環；不得用新 Git Tag、重命名或覆蓋 branch ref 假裝完成。
