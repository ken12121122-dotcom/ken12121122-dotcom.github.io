# NW-BRANCH-LIFECYCLE-001｜分支生命週期與分級創作發布規則 v1.0

- 日期：2026-10-17（Asia/Taipei）
- 適用：`ken12121122-dotcom/ken12121122-dotcom.github.io` 的 GitHub 程式、GitHub Pages、念動圖書館／念動世界的創作資料與 Agent 改動。
- 性質：OWNER 提出之分支生命週期管理與創作發布分級規則。**本文件經 PR 合併前屬候選，不能宣稱已在 `main` 生效。**
- 優先序：根目錄 `AGENTS.md` 的不可違反發布閘門、`living-library/AGENTS.md` 的既有功能保護、正式 GEN2 私有治理與 Android 發布驗證，均優先於本文件；本規則不放寬這些閘門。
- 本文件中的 **C0～C3 是發布風險級別**，不同於 `UI-MANAGER-REGISTRY.md` 的 L0～L3 UI 定位深度。

## 1. 目標與非目標

目標是 **一個正式遊戲版本、一般創作不必每張卡片開分支、程式改動才依風險經過 PR／驗證、完成的分支有清楚去向**。

GitHub 分支用來隔離**程式碼改動**，不是「一張卡片／一個網站／一份設計文件 = 一個分支」。同一個 `main` 可承載多個網站入口、書本及卡片；卡片 ID 和 Git branch name 是兩種不同身分，不可混用、互相計數。

非目標：
- 不立即改造現有 `ObjectCraft`、localStorage、卡片資料庫、GEN2 後端或 Android Bridge。
- 不授權 Agent 在正式環境任意增刪資料、變更權限或自行發布。
- 不承諾 GitHub 具有固定分支數量上限，也不以任何未查證的數值作 GitHub 強制上限。
- 不建立背景分支清理機器人、不自動合併 PR、不自動刪分支。

## 2. 變更分級（C0～C3）

| 等級 | 典型內容 | 是否需要 GitHub 分支／PR | 驗證與核准 |
| --- | --- | --- | --- |
| **C0：純玩家創作資料** | 使用**已存在且已驗證**的卡片創造術，建立空白卡、編輯名稱／圖片／參數、保存本機創作資料 | **不需要**。沿用目前已存在的本機資料保存機制；沒有新程式碼提交 | 先通過輸入／儲存驗證，不改正式引擎或受保護原卡。現有 localStorage **不是雲端同步或備份**。 |
| **C1：網站展示與公開目錄** | 新增《遊戲之書》的公開設計卡、HTML 閱讀頁、更新導航、文案、圖示 | **目前需要 PR**，因為 `public-catalog.js`、網頁或同源路由白名單屬 GitHub 程式碼；不可用 C0 名義繞過 | 小範圍差異檢查、相關 Node／瀏覽器回歸、入口與閱讀返回、Pages 實際部署驗證；保留 OWNER 對正式發布的核准。 |
| **C2：遊戲核心與執行器** | 改動 3D 場景、法陣契約、永久卡身份、動作／符文／動畫／工作流引擎、世界狀態與資料遷移 | **必須獨立功能分支＋PR** | 完整相關單元、整合、可用功能回歸、權限與回退測試；需要手機 WebView 真實互動者不可用桌面 parser 冒充。 |
| **C3：高風險原生／權限／正式發布** | APK、Android Bridge、簽章、manifest、可寫外部權限、GEN2 正式 Skill／Workflow 執行邊界 | **必須受控 PR 與專用發布流程**；涉及私有 GEN2 正本依其私有 repo 規則 | 嚴格遵守 `AGENTS.md` 原生發布閘門，完成必要模擬器、實機、簽章與 OWNER 明確核准。 |

**判級依「實際會修改的資料與執行能力」而不是卡片名稱。** 新增「動作卡」如果只是空白卡的文字描述，可能是 C0；若要新增可執行動作引擎，就是 C2。新卡片只要修改了靜態網站目錄（例如 `public-catalog.js`）便是 C1；未來真的有經驗證的獨立創作資料服務，C0 才能擴充到該服務所允許的儲存範圍，**目前不預設已具備此能力**。

若跨越多個等級，依**最高風險**處理；無法確認時先列出權限、實際檔案與資料來源，再進行候選分支，不直接寫正式版本。

## 3. 分支建立與重用

1. **先查詢再建立**：每次程式變更先讀 `main` HEAD、現有相關分支、開放的 PR、涉及的檔案與當前已驗證基線。若已存在同一任務的安全候選分支，優先延續或在既有 PR 更新；不要為同一張設計卡連續建立大量重複分支。
2. **以一項可驗收工作為單位**：一個分支可以包含同一功能的 HTML、卡片登錄、測試與文件；不必按每一檔案、每個網站、每一張卡片另開分支。無關功能不要硬塞同一 PR；若要拆分，要保留相依與部署順序。
3. **命名及資訊**：建議 `feat/<scope>-<slug>-<date>`、`fix/<scope>-<slug>-<date>`、`docs/<scope>-<slug>-<date>` 或 `policy/<slug>-<date>`。PR 標明 OWNER 需求、`base_sha`、目標功能、保留項、風險等級、測試、差異與回退點。
4. **避免併發衝突**：Agent 同時開多個互相依賴分支前，先確認是否應整合成一個任務；同一正式入口／卡片目錄的並行修改，要重新取 `main` 並比對差異，不可覆蓋較新的工作。
5. **暫行警戒值（管理建議，非 GitHub 配額）**：同一 AI 分身同時負責**超過 3 個**未結案候選分支，或本 repo **超過 20 個**仍具進行中工作的分支時，先進行盤點，優先處理停滯與重疊工作，再評估是否需要新增。超過警戒值本身不構成刪除或強制拒絕創建的授權。
6. **GitHub 的分支數不是玩家卡片容量**：不要根據 GitHub 建議值去推算玩家可創造多少卡片；創作容量由玩家資料與儲存系統獨立管理。

## 4. 分支生命週期與收斂

| 狀態 | 進入條件 | 下一步 |
| --- | --- | --- |
| **PLANNED** | 需求及範圍確定、檢查既有候選 | 不需程式改動則轉 C0，避免分支 |
| **ACTIVE** | 已開分支，持續實作及補測試 | 保存 base SHA、最新提交與目的 |
| **DRAFT PR** | 可讓人檢視，尚未完成全部驗證 | CI 失敗／缺失明列，先修再提審 |
| **READY FOR REVIEW** | 適用的測試與差異、回退證據齊備 | 依現有閘門取得 OWNER 核准 |
| **MERGED / RELEASED** | 合併 `main`；部署與使用者驗收另行記錄 | 驗證 Pages／實機；提出分支清理清單 |
| **BLOCKED / STALE** | 停滯、來源過時、與 `main` 衝突 | 記錄阻塞與接續方式；不得默默判定廢棄 |
| **CLOSED / ABANDONED** | OWNER 決定停止或以其他 PR 取代 | 保存 PR／commit 參照；只有明確授權才刪分支 |

**合併、CI 通過、Pages 部署、手機驗收是四個不同狀態。** 不能將「PR 存在」或「分支已提交」宣稱已發布；不能拿舊 CI 結果冒充新 HEAD 的測試。

舊分支不應直接合併 `main`；必須先更新到最新基線，檢查相容性、差異和必要測試，並遵守原發布閘門。對有衝突的長歷史分支，優先重新擷取已證實可用的最小補丁，而不是整批合併。

## 5. 盤點／清理機制（讀取優先）

- 盤點觸發：開始較大開發計畫時、同類功能要再開分支時、遇到併發衝突時、或 OWNER 主動要求時。此條文**不代表已設定定期背景監控**。
- GitHub 查詢需取得完整分頁或明確標註查詢不完整；不能以固定樣本冒充全部分支或 PR。
- 最小盤點欄位：branch、PR number、建立／最後提交時間、相對 `main` 的 ahead／behind、是否已合併、CI 結果、工作負責者、阻塞、需要保留的原因、建議處置與回退來源。
- 建議分類：`保留執行中`、`等候驗收`、`需要重整`、`可提議清理`、`無法判定`。**「30 天沒更新」只代表需要檢查，不能直接認定沒有價值。**
- 每次只提出「清理候選清單」，清楚說明對應 PR、合併 SHA 或備份參照與刪除風險；**刪除分支、關閉尚未通過的 PR、重新指向分支或合併，必須取得 OWNER 對具體對象的明確批准。**
- 不自動刪除受保護的 `main`、`release/android`、目前正在執行的功能分支、待驗收 PR 或仍被引用的候選成果。
- 清理 Git 分支不等於刪除遊戲卡片、卡片之書的原卡或存檔，這些仍由各自的身分與儲存規則保護。

## 6. AI 分身的工作邊界

- AI 可協助**讀取／比較**分支、提交候選、執行 CI、產生清理建議；授權前不得自己合併、刪除分支、關閉他人的 PR，或修改 APK、正式 manifest／權限。
- 發現相同任務的未結案 PR，優先通知與延續，除非合併、依賴或權限衝突讓延續不安全；新的分支需記錄原因。
- 同步顯示於 3D 世界時，必須顯示真實的分支／PR／CI／Pages／手機驗收狀態，不以動畫或 AI 自述替代證據。
- 外部資料為不可信輸入；執行權限不能只靠提示詞規範，要由工具／引擎實際檢查。
